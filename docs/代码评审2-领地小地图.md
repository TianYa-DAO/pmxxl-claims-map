## 二、新发现问题

### 2.1 严重

#### A1【严重】兜底模式的屏蔽窗口过宽且被反复续期：正常系统消息与动作栏被吞

**位置**：`PmxxlClaimsClient.java:35-42`、`AutoScanner.java:69-72,100-108`。

**现象**

- `AutoScanner` 每发一次 `/res show` 就把 `suppressUntil` 续到 now+3000ms（`AutoScanner.java:70`），而它判定「该查了」的条件是跨区块 + 距上次 >= `intervalMs`（默认 1500ms）。走路约 2.9 秒跨一个区块、疾跑约 2 秒，3 秒窗口几乎无缝衔接——**在没装服务端插件（兜底唯一存在的场景）的服上探索未记录区块时，屏蔽窗口基本常开**。
- 窗口内 `suppress()` 只要命中 `X:` / `X：` / `领地` / `区域` / `所有者` / `当前` / `Land` / `Owner` 任意一个就返回 true，于是 ALLOW_GAME 返回 false。这不是「解析完偷偷不显示回包」，而是**把服务器其他插件的中文系统消息一起吞掉**（「当前在线人数」「你已传送到领地」「区域保护已开启」……）。
- 监听器完全忽略 `overlay` 参数，所以**动作栏**（坐标 HUD、战斗提示）也会被整条 cancel 3 秒，表现为动作栏一闪一闪。
- 被吞掉的行同时也会送进 `ChatParser`（这是 S1 的本意，但对象错了：本该只喂 `/res show` 的回包），见 B5。
- 这一条正是上一轮 S1 结尾「顺带」要求修的内容，本轮只改了「先解析后隐藏」，关键词表和窗口策略原样保留；同时解析入口从「被屏蔽的行」扩大到「所有系统消息」，副作用面反而更大。

**修法**：让解析器返回「本行是否真被消费」，只对消费成功的行做隐藏，并把关键词收窄到 `/res show` 的固定前缀：

```java
// PmxxlClaimsClient
boolean consumed = client.world != null
        && ChatParser.accept(line, MinimapRenderer.worldId(client.world));
if (consumed && AutoScanner.inWindow() && !overlay) {
    AutoScanner.closeWindow();   // 收到回包立即关窗，grace 200ms
    return false;
}
return true;

// AutoScanner.suppress：只认 领地: / 所有者: / Land: / Owner: / X:
```

这样即使窗口开着，普通聊天也不会消失；且窗口在收到第一条回包后就关闭，不再固定 3 秒。

#### A2【严重】空结果告警的去重写反：无人区每个玩家每 2 秒一条 WARNING

**位置**：`ClaimService.java:114-117`（配合 `:29` 的 TTL 与 `ClaimPublisher.java:47` 的 40 tick 巡检）。

```java
if (claims.isEmpty() && EMPTY_WARNED.add(worldName)) {
    logger.warning("no residences found within " + radius + " chunks of " + worldName + " (chunk index may be missing)");
    EMPTY_WARNED.remove(worldName);   // ← 立刻删掉，add 永远为 true
}
```

`add` 成功马上 `remove`，等于每次都打。而 `build` 在「半径内确实没有领地」这种**完全正常**的情况下也会走到这里，触发频率是「每个玩家每 2 秒一次」（快照 TTL 与巡检周期相同，见 M1）：50 人在线、大半在野外时上限约 **25 条 WARNING/秒**（约 9 万条/小时），控制台与日志文件会被刷爆，真正的错误反而被淹掉；告警文案「chunk index may be missing」也是误报。

**修法**：直接删掉这段（空结果是常态，不是异常）。如果确实想保留「世界索引缺失」探测，用 `ResidenceManager#getResidences()` 的全量表判断「该世界是否存在任何领地」，并用 `Map<String, Long>` 做 5 分钟一次的真实限流，日志级别降为 `fine` 或 `info`。

#### A3【严重】兜底库的键不含服务器标识：跨服串数据，并让自动扫描跳过这些区块

**位置**：`ClaimStore.java:43-45,47-53`；`AutoScanner.java:65-68,87-98`；`PmxxlClaimsClient.java:33-34,62-68`。

`ClaimStore` 的 key 是 `world + '|' + name`，而 `world` 是维度 id（`minecraft:overworld`），**每个服务器的每个主世界都叫这个名字**；`resetSession()` 只清 ClaimCache/AutoScanner/ChunkColorCache，从不清 ClaimStore，也不记服务器地址。后果：

1. 玩家从 A 服（有插件或走过兜底）换到 B 服（没插件）时，B 服主世界会直接画出 A 服的领地色块；
2. `AutoScanner.insideKnownClaim` 读的是同一个库，命中后 `remember(key, now)` 直接 return **不发 /res show**，这些区块 10 分钟内不会再被确认；
3. 数据还会落盘，重启后继续污染。

**修法**：key 改为 `serverAddress + '|' + world + '|' + name`（`client.getCurrentServerEntry().address`），JOIN 时若地址与上次不同则 `ClaimStore.forgetServer(old)`（顺便把现在没人调用的 `forgetWorld` 换成它）；或者干脆按服务器分文件/分段。

### 2.2 中等

#### B1 每 2 秒对每个在线玩家完整 encode+deflate，即使内容一个字都没变

**位置**：`ClaimPublisher.java:79-94,109-117`。

`refresh()` 无条件 `runTaskAsynchronously(encodeSafely(...))`，哈希去重发生在 `deliver()` 里、**编码之后**。50 人时每秒 25 次 encode+deflate（每次 5～60 KB），其中只有每 10 秒一次的心跳真正需要发。CPU 与分配都不算大，但完全是白烧的，而且把 `encodeSafely` 的裁剪日志路径也带热了。

**修法**（任选其一，改动都小）：
1. 在 `Cached` 里懒加载并缓存 `byte[] payload`（同一 Snapshot 只编一次；同区块的多个玩家天然共享）；
2. 给 `Snapshot` 加一个内容版本号，`refresh` 前先比对「上次发给该玩家的内容版本 + 心跳时间」，没变就不排 async；
3. 至少把 `heartbeat` 判断提前到 `collect` 之前，非心跳且玩家没跨区块时直接 return。

#### B2 `refresh()` 不捕获 `collect()` 异常，`refreshAll()` 也没有逐玩家 try/catch

**位置**：`ClaimPublisher.java:72-79,97-101`；调用点 `PlayerListener.java:35,46`。

上一轮 S4 只给「发送」加了 try/catch，`service.collect(player)`（内部走 Residence、`getLocation`、`getAreaMap`）仍在裸奔。一旦某个玩家的数据让 Residence 抛 RuntimeException：`refreshAll` 的 for 循环直接中断，**这一轮后面所有玩家都收不到包**（调度器只把这次任务记为异常）；`onMove` 里抛出的异常会被 Bukkit 的 `SimplePluginManager` 按监听器捕获并打印「Could not pass event ...」，主线程不崩，但该玩家这一次刷新及其后的调度都不会执行，而且每个跨区块 tick 都会重复这条错误日志。

**修法**：`refresh(player)` 整体 try/catch（collect + revision + 调度全包），`refreshAll` 里每个玩家再包一层，异常只记日志并 `lastHash.remove`。

#### B3 客户端 `active` 永不过期：服务端插件被卸载/重载后地图永久冻结，兜底也不会接管

**位置**：`ClaimCache.java:9,15-27`；`AutoScanner.java:37-39`。

`active` 一旦为 true 就只能靠 JOIN/DISCONNECT 复位。运维场景里很常见：管理员在玩家在线时 `/reload` 或卸掉 PmxxlClaims（或者插件自己 disable），此后客户端收不到任何包，`AutoScanner` 因为 `active` 一直 return，兜底也不查——**小地图停在最后一帧旧数据上，无提示、无超时**。

**修法**：`accept` 里记 `lastPacketAt`；`isActive()` 改为「active && 60 秒内收到过包」，过期后允许兜底查询并保留旧图（可加一个淡色/问号标记表示数据已陈旧）；不要简单把 active 置 false，否则又会回到 S6 的抖动。

#### B4 DISCONNECT 回调在 netty 线程上，`resetSession` 直接清非线程安全的 HashMap

**位置**：`PmxxlClaimsClient.java:33-34,62-68`；`ChunkColorCache.java:14,73-75`；`AutoScanner.java:16,25-31`。

fabric-api 源码核实：`ClientPlayConnectionEvents.DISCONNECT` 由 `AbstractNetworkAddon#handleDisconnect` 触发，而 `ConnectionMixin` 在 `channelInactive` 与 `handleDisconnection` 两处调用它——**都在 netty 线程**（不是渲染线程）。`resetSession()` 里的 `ChunkColorCache.clear()`（普通 `HashMap`）、`AutoScanner.reset()`（普通 `LinkedHashMap`）会与渲染线程/客户端 tick 线程并发读写，轻则丢条目，重则 `HashMap` 内部结构损坏或 `remember()` 的迭代器抛 `ConcurrentModificationException`。

**修法**：`resetSession` 一律投递到客户端线程执行：

```java
ClientPlayConnectionEvents.DISCONNECT.register((h, c) -> c.execute(PmxxlClaimsClient::resetSession));
ClientPlayConnectionEvents.JOIN.register((h, s, c) -> c.execute(PmxxlClaimsClient::resetSession));
```

（JOIN 大概率已经在渲染线程，但统一投递没有代价。）

#### B5 所有系统消息都进解析器：会造出 `unnamed` 伪领地并持久化

**位置**：`PmxxlClaimsClient.java:35-42`；`ChatParser.java:45-58,89-103`；`ClaimStore.java:47-59`。

ALLOW_GAME 现在对**每一条**系统消息（含动作栏）调用 `ChatParser.accept`，与是否处于查询窗口无关。于是：

- 任何一条普通系统消息里出现 1 个 `X:.. Y:.. Z:..` 三元组，再在 1.5 秒内出现第二个，就会以 `unnamed` 为名生成一条领地（`ChatParser.java:52-55,101`），经 `ClaimStore.put` 写入内存并最终落盘 `pmxxlclaims-claims.json`；
- 任何含「领地: / 区域: / Land:」的公告也会被当成领地名的开始；
- 服务端插件正常工作时（推流生效），兜底不参与渲染，但这些垃圾仍会落盘、并让 `ClaimStore.version` 变化触发渲染缓存重建。

**修法**：只在查询窗口内解析（`AutoScanner.inWindow()`），忽略 overlay 行，且没有前置名字行时丢弃坐标（不再造 `unnamed`）。

#### B6 服务端字符串没有长度上限，客户端 256 字节硬上限会把整包静默丢弃

**位置**：`net/ClaimCodec.java:74-78`；客户端 `ClaimCodec.java:17,104-112`；`ClaimCache.java:15-22`。

`writeString` 对名字/owner/世界不做任何截断；客户端 `MAX_STRING = 256`，超一个字节就 `throw new IOException` → `decode` 返回 null → `ClaimCache.accept` **直接 return，不打任何日志**。只要附近有一条名字（或父链拼出来的 path）超过 256 字节的领地，这个玩家收到的整包都会被丢掉；而服务端已经把哈希记成「已发」，之后只在 10 秒心跳时重复送同一个坏包。排查时表现为「客户端 claims 数一直是 0，服务端 debug 明明有数据」。

**修法**：服务端 `writeString` 截断到 96/128 字节（UTF-8 且不截断半个字符）；客户端把 `MAX_STRING` 提到 512，并在拒绝时 `LOGGER.warn` 一次（带长度），别静默。

#### B7 `REF_CACHE` 最多缓存 4096 个 (2R+1)^2 的 ChunkRef 列表：约 100 MB 内存

**位置**：`ClaimService.java:35,121-139`。

默认 R=16 时每个 key 是 1089 个 `ChunkRef`（每个约 24 字节）＋一个 1089 槽的数组，约 30 KB；`size() > 4096` 才整表清空，稳态内存约 **120 MB**（对象头/对齐算下来 100 MB 上下），而且它是 static、跨 reload 存活。M1 加它是为了省分配，但一个移动中的玩家每跨一个区块就新建一个 key，缓存对他毫无用处，只是在堆里堆垃圾。

**修法**：上限降到 256～512 并改成按访问顺序淘汰（或只缓存「以 (0,0) 为中心的相对偏移」，查询前平移后复用同一份数组——不过 `ChunkRef` 没有平移 API，最省事的是降上限）；更好的做法是把「玩家所在区块 → 快照」缓存做长（见 M1），让 REF_CACHE 只服务常驻区块。

#### B8 `AutoScanner` 先写 `lastChunk` 再判间隔：被间隔挡下的区块永远不会补查

**位置**：`AutoScanner.java:52-59`。

`lastChunk = chunk` 在 `now - lastQueryAt < intervalMs` 判断之前，于是「刚跨进新区块但距上次查询不足 1.5 秒」时直接 return，而这个区块已经被记为「当前区块」，**下次 tick 因为 `chunk == lastChunk` 再也不会进来**。疾跑/坐船/骑马的玩家会因此跳过大量区块，兜底发现率下降。

**修法**：把 `lastChunk = chunk` 移到「真正发出查询」之后；或者把间隔判断放在 `chunk == lastChunk` 之前（不更新 lastChunk）。

#### B9 插件 disable 之后仍可能向 scheduler 投递任务

**位置**：`ClaimPublisher.java:50-58,82-94`（`stop()` 只 cancel 周期任务）。

`onDisable` 时若还有在飞的异步编码，回调里的 `Bukkit.getScheduler().runTask(plugin, ...)` 会在「插件已禁用」状态下抛 `IllegalPluginAccessException`，在控制台留下一条与业务无关的异常；`markDirty` 排下的 `runTask` 同理会。

**修法**：异步回调开头与 `markDirty` 的 runnable 里加 `if (!plugin.isEnabled()) return;`。

- **C1 每帧 121 次 `toString()`**：`ChunkColorCache.java:20` 在每个区块上 `world.getRegistryKey().getValue().toString()`，`MinimapRenderer.java:73` 每帧调 121 次；加上 `:77,86` 两次 `worldId(world)`，约 7k 个小字符串/秒。改成以 `RegistryKey<World>` 为 key、每帧只算一次 id。

## 三、仍然存在的问题

1. **M18 名存实亡**：`getResidences` 永不返回 null（javap 证据见附录 B），`status=1` 分支永远走不到；客户端「收到 status!=0 保留旧缓存」也是死代码。要么删掉 status 字段（协议减 1 字节），要么换一种可判定的信号（例如服务端统计该世界在 Residence 里的领地总数，为 0 时发 status=1 并附原因）。
2. **M1 的性能问题没有实质缓解**：快照 TTL 与巡检周期都是 2 秒，稳态命中率≈0，50 人仍等于 25 次/秒 × 1089 次 `Map.get`（约 2.7 万次/秒）；半径调到 32 时是 4225 次/人（约 10 万次/秒）。建议把快照 TTL 提到 15～30 秒并完全依赖「领地事件 + 玩家跨区块」失效，或者干脆只在 dirty/跨区块/心跳到期时刷新，而不是固定 2 秒全量巡检。
3. **兜底数据只增不减**：`ClaimStore` 既没有 TTL 也不处理改名/删除（`updatedAt` 只用于淘汰），被删掉的领地会永远留在地图上，`insideKnownClaim` 还会因此跳过确认；配合 A3 的跨服问题，长期使用会越来越脏。
4. **S6 的第三条现象仍在**：在没有 Residence 的服务器上，客户端依旧每个区块发一次 `/res show`，收到的是「未知命令」并显示在聊天里（`suppress` 不匹配），配合 10 分钟 TTL 会持续刷。建议加连续失败退避（连续 N 次没有解析到坐标就把 interval 指数放大，上限 10 分钟），或在首次失败后提示一次并可配置关闭。
5. **兜底发现能力被高估**：Residence 的 `/res show` 不带参数时只显示「你所在的领地」（`ResidenceManager#printAreaInfo`），所以只有**站在领地里**那一次才可能记下来；站在领地旁边不会发现它。文档里「走进没记录过的区块时问一次」容易被理解成「附近领地都能发现」，建议在文档里写清楚。
6. **owner 字段全程无用**：服务端 `send-owner`（默认 false）编进协议，客户端 `ClaimCodec.Claim.owner` 存下来后没有任何读取点；`ClaimData.FLAG_SUBZONE` 只用 1 bit，flags 还空着 7 位。要么实现 PLAN 里的「第二行归属者」，要么把 owner 从协议里删掉（每条省 1 字节 + 配置项）。
7. **两套 Box 类型**：`ClaimCodec.Box` 与 `ClaimStore.Box` 字段完全一样，渲染层每次都要手工转换（`MinimapRenderer.java:104-107,117-120`）；合并成一个即可（N10 的残留）。
8. **`ChunkRef.hashCode = x ^ z`**（javap 证据）：Residence 内部实现，改不了；目前只靠 REF_CACHE 少建对象，桶冲突放大的问题仍在。若将来要彻底解决，方向是「遍历该世界领地列表做 AABB 相交」而不是 `getResidences`。
9. **`accepts()` 的运行时前提未验证**：M17 把默认值改成「只发给注册了频道的客户端」，一旦 Paper 侧不认 Fabric 的 `minecraft:register`，表现是**所有人都收不到**（旧代码至少有 `channels.isEmpty()` 兜底）。上线前必须按附录 D 第 1 条实测。
10. **文档滞后**：C6 列的三处，加上「心跳 10 秒」在客户端文档里写成了「10 秒一次心跳，内容不变也发」（是对的），但服务端文档仍写「哈希不变就不发」，需要一起改。

## 本轮修复（2026-10-30，回应复审）

针对本报告的新发现，已修并重新验证：

1. A1 屏蔽窗口过宽：窗口从 3 秒收到 1.5 秒；匹配条件收窄为「同一行同时含 X:/Y:/Z:」或明确的「不在领地内」提示；动作栏（overlay）一律不屏蔽；且只在兜底查询后才生效。
2. A2 警告去重写反：EMPTY_WARNED 的 add/remove 逻辑删除，改成按世界 60 秒一次的限频记日志，并降为 FINE 级，不再刷 WARNING。
3. A3 跨服串数据：ClaimStore 的键改为「服务器地址|维度|名字」，JSON 里也带 server 字段；forWorld/forgetWorld 都按当前服过滤，换服不会画出上个服的领地。
4. B1 内容不变仍全量编码：主线程先算 64 位内容签名，签名未变且未到心跳直接跳过，异步编码只在真有变化时发生。
5. B2 collect 异常中断整轮刷新：refresh 内 try/catch，单个玩家异常只跳过该玩家。
6. B3 活跃状态永不过期：ClaimCache 改成「收到过包 + 60 秒内有包」才算活跃；插件被卸载 60 秒后自动回落到聊天兜底，地图不会永久冻结。
7. B4 DISCONNECT 在 netty 线程清缓存：JOIN/DISCONNECT 都改为 client.execute(...) 回主线程执行清理。
8. B5 无名伪领地：坐标只在已经拿到领地名之后才累积，孤立的坐标行直接丢弃，不会再生成 unnamed 领地和落盘。
9. B6 服务端字符串无上限：编码端把名字/owner 截断到 120 字节，客户端上限 256 字节，包不会再因为超长字符串被整包丢弃。
10. B7 REF_CACHE 过大：上限从 4096 收到 256 条，最坏内存从百 MB 级降到 MB 级。
11. B8 间隔挡下的区块永不补查：lastChunk 改为通过间隔判定之后才写入，被节流拦下的区块下一 tick 会重试。
12. B9 停服后仍投递：refresh 与 deliver 都检查 plugin.isEnabled()；停用后不再调度异步编码。
13. M18 status 死代码：去掉永不成立的 null 分支（已核实 getResidences 不会返回 null），status 字段保留但恒为 0，客户端仍按「status!=0 保留旧缓存」处理。
14. M1 缓存命中率：快照 TTL 提到 3 秒，巡检周期从 2 秒改成 3 秒，稳态命中率显著提高。
15. M5 LRU：ChunkColorCache 改为 LinkedHashMap 访问序 LRU，不再整表 clear。
