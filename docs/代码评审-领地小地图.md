评审方式：只读评审，未修改任何源码，未执行构建；依赖 API 通过 `javap` 反编译 `Residence5.1.6.2(1).jar`、`spigot-api-1.21.4`、`paper-1.21.5`、fabric-api 源码 jar、loom 映射后的 1.21.11 jar 核实。

---

## 结论摘要

1. **协议/推送主链路是通的，但聊天兜底链路被自己的屏蔽逻辑 100% 打死**（`ALLOW_GAME` 先于 `GAME`，`/res show` 的回包被吞掉，`ChatParser` 永远收不到），服务端没装插件时等于没有兜底。
2. 客户端解码器对长度/数量字段零校验，任意一个畸形包就能 OOM、抛未捕获异常并被 Fabric 重抛成断连；服务端则对 1 MiB 包上限零防护，超限异常会让整轮刷新中断。
3. 服务端"内容哈希不变就不发"导致 30 秒静默后客户端误判为"服务端无插件"，自动查询器开始每 1.5 秒刷 `/res show`；同时领地变更事件里同步 `refreshAll`，批量改领地会直接卡死主线程。

## 1. 严重问题（会导致不工作 / 崩溃 / 数据错误）

### S1【最严重】聊天兜底链路 100% 失效：`/res show` 的回包被自己的 `ALLOW_GAME` 吞掉，`ChatParser` 永远收不到

**位置**
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/PmxxlClaimsClient.java:31-38`
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ChatParser.java:23`
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/AutoScanner.java:62-63`、`:79-87`

**现象**
服务端没装插件（或推送断流）时，`AutoScanner` 发出 `/res show`，紧接着把 3 秒屏蔽窗口打开：

```java
// AutoScanner.java:62-63
suppressUntil = now + SUPPRESS_MS;   // 3000ms
player.networkHandler.sendChatCommand("res show");
```

`/res show` 的回包在 3 秒内到达，内容必然含 `领地` / `所有者` / `X:`，于是 `suppress()` 返回 true → `ALLOW_GAME` 返回 false。

而 Fabric 的事件顺序是**互斥**的（`fabric-message-api-v1` 的 `ChatListenerMixin#handleSystemMessage` 已核实）：

```java
if (ALLOW_GAME.invoker().allowReceiveGameMessage(...)) {
    message = MODIFY_GAME...;
    GAME.invoker().onReceiveGameMessage(...);   // ← 只有放行才会进这里
} else {
    GAME_CANCELED...;
    ci.cancel();
}
```

所以 **`ChatParser.accept`（注册在 `GAME` 上）永远看不到自动查询的结果**，`ClaimStore` 永远是空的，`insideKnownClaim` 永远 false，于是继续查、继续吞——兜底子系统实际上是死代码。只有玩家自己手动敲 `/res show`（此时 `suppressUntil == 0`）才能解析成功。

**修法（二选一，推荐第一种）**

1. 在 `ALLOW_GAME` 里"先解析、再隐藏"，放弃在 `GAME` 里解析：

```java
ClientReceiveMessageEvents.ALLOW_GAME.register((message, overlay) -> {
    String line = message.getString();
    MinecraftClient client = MinecraftClient.getInstance();
    if (ClientConfig.autoScan() && AutoScanner.shouldHide(line)) {   // 3s 窗口 + 关键词
        if (client.world != null) ChatParser.accept(line, MinimapRenderer.worldId(client.world));
        return false;                       // 吞掉显示，但数据已经进了解析器
    }
    return true;
});
// GAME 上只保留"非屏蔽消息"的解析（或者干脆不注册，统一走 ALLOW_GAME）
```

2. 或者保留 `GAME` 解析、改用 `MODIFY_GAME` 把命中屏蔽窗口的行替换成空文本（`Text.empty()`），即"显示层隐藏、事件照常触发"。

**顺带**：`suppress()` 的关键词表包含 `当前`、`Land`、`Owner`、`X:`，命中面过宽——3 秒窗口内服务器任何含这些字样的系统消息都会消失。建议只匹配 `/res show` 的固定前缀（`领地:` / `所有者:` / `Owner:` / `Land:`），并且把窗口缩到"从发包到收到第一条回包为止"。

### S2 解码端零上限：一个畸形包就能 OOM / 抛未捕获异常 → 断连

**位置**
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:46-47`（`new ArrayList<>(worldCount)`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:51-52`（`new ArrayList<>(claimCount)`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:59-60`（`new ArrayList<>(areaCount)`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:95-100`（`new byte[length]`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:79-93`（varint 允许读到**第 6** 字节：`position > 35` 才抛，第 6 次 `shift=35` 会被 Java 取模成 3，返回值可以是负数或彻底错乱）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCache.java:26-30`（只判 `result == null`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/PmxxlClaimsClient.java:30`

**现象与原理**
1. `readVarInt` 的边界检查放在 `position += 7` 之后，且条件是 `> 35`，所以第 5 字节（`<< 28`，符号位）不会被拦；只要最高位是 1，返回值就是**负数**，第 6 字节更会因为 `<< 35` 被取模成 `<< 3` 而彻底错乱。`worldCount = -1` → `new ArrayList<>(-1)` 抛 `IllegalArgumentException`；`readString` 的 `length = -1` → `NegativeArraySizeException`。这两个都不是 `IOException`，`catch (IOException)` 接不住。
2. 就算不溢出，`worldCount = 100_000_000` 会让 `new ArrayList<>(1e8)` 直接申请 ~400 MB → OOM。
3. 异常从 receiver 抛出后，Fabric 的 `AbstractChanneledNetworkAddon#handle` 只 `logger.error` 然后 `throw ex`；`ClientPlayNetworkHandler` 没有兜底，最终走到 netty 的 `exceptionCaught` → **"Internal Exception" 断连**（OOM 则更糟）。

**修法**

```java
private static final int MAX_WORLDS = 8;
private static final int MAX_CLAIMS = 4096;
private static final int MAX_AREAS  = 256;
private static final int MAX_STRING = 256;
private static final int MAX_RAW    = 1 << 20;   // 1 MiB，和服务端上限对齐
private static final int MAX_BODY   = 4 << 20;

public static Result decode(byte[] raw) {
    if (raw == null || raw.length < 5 || raw.length > MAX_RAW) return null;
    ...
    int worldCount = readVarInt(in);
    if (worldCount < 0 || worldCount > MAX_WORLDS) return null;
    ...
    if (claimCount < 0 || claimCount > MAX_CLAIMS) return null;
    ...
    if (areaCount < 0 || areaCount > MAX_AREAS) return null;
    ...
    if (length < 0 || length > MAX_STRING || length > in.available()) return null;
}

private static int readVarInt(DataInputStream in) throws IOException {
    int value = 0;
    for (int shift = 0; shift < 32; shift += 7) {
        int b = in.readUnsignedByte();
        value |= (b & 0x7F) << shift;
        if ((b & 0x80) == 0) return value;
    }
    throw new IOException("varint too long");
}
```

外层再加一层兜底，保证异常不逃出网络回调：

```java
ClientPlayNetworking.registerGlobalReceiver(ClaimPayload.ID, (payload, ctx) -> {
    try { ClaimCache.accept(payload.data()); }
    catch (Throwable t) { LOGGER.warn("bad PMC1 payload", t); }
});
```

### S3 deflate 炸弹：`inflate` 无输出上限

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCodec.java:102-123`（关键在 `:105` 初值、`:108-116` 循环）

**现象**：`new ByteArrayOutputStream(data.length * 3 + 64)` 只是初始容量，循环没有任何总量上限。1 KiB 的合法 deflate 流可以膨胀到 1 GiB，直接把客户端堆打满；服务端日志里也看不出异常（客户端侧崩溃）。

**修法**

```java
private static byte[] inflate(byte[] data) throws IOException {
    if (data.length > MAX_RAW) throw new IOException("too big");
    Inflater inflater = new Inflater();
    inflater.setInput(data);
    ByteArrayOutputStream out = new ByteArrayOutputStream(Math.min(data.length * 4, MAX_BODY));
    byte[] chunk = new byte[4096];
    try {
        while (!inflater.finished()) {
            int n = inflater.inflate(chunk);
            if (n == 0) {
                if (inflater.needsInput() || inflater.needsDictionary()) break;
                continue;
            }
            if (out.size() + n > MAX_BODY) throw new IOException("inflate bomb");
            out.write(chunk, 0, n);
        }
    } catch (DataFormatException e) { throw new IOException(e); }
    finally { inflater.end(); }
    return out.toByteArray();
}
```

（`MAX_BODY` 取 4 MiB 足够：1089 chunk 半径下真实报文通常 5~60 KB。）

### S4 服务端发包无大小保护 + 无逐玩家 try/catch：一个玩家超限让整轮推送全灭

**位置**
- `server/src/main/java/com/horizonkk/pmxxlclaims/net/ClaimCodec.java:24-40`（`encode` 无上限）
- `server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:53-61`（collect/encode/send 裸奔）
- `server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:64-68`（`refreshAll` 循环无 try/catch）

**现象**
`CraftPlayer#sendPluginMessage` 第一步就是 `validatePluginMessage`，超过 `1048576` 字节抛 `MessageTooLargeException`（RuntimeException，已核实）。`refreshAll` 是普通 for 循环，一个玩家抛异常 → **本次 tick 剩下的所有玩家都收不到包**，且异常冒到 `BukkitScheduler`（打印 "Task #N generated an exception"）。另外 `lastHash.put` 在 `sendPluginMessage` 之前（`:56`），一旦发送失败，哈希已被记下，内容不变就再也不会补发——这个玩家会永久停在旧数据上。

**修法**

```java
public void refresh(Player player) {
    if (player == null || !player.isOnline() || !accepts(player)) return;
    try {
        ClaimService.Snapshot snapshot = service.collect(player);
        byte[] data = ClaimCodec.encode(snapshot.worlds(), snapshot.claims());
        if (data.length > MAX_PAYLOAD) {                 // 建议 32768，留足余量
            // 方案 A：按 claims 二分分片，客户端按 batchId 合并（协议要加字段）
            // 方案 B：降级，只发离玩家最近的 N 条 / 只发包围盒相交的
            // 方案 C：直接跳过并 log warning（至少不能抛）
            plugin.getLogger().warning("payload too large for " + player.getName() + ": " + data.length);
            return;
        }
        int hash = Arrays.hashCode(data);
        if (Objects.equals(lastHash.get(player.getUniqueId()), hash)) return;
        player.sendPluginMessage(plugin, PmxxlClaims.CHANNEL, data);
        lastHash.put(player.getUniqueId(), hash);         // 成功后再记账
    } catch (RuntimeException ex) {
        plugin.getLogger().log(Level.WARNING, "refresh failed for " + player.getName(), ex);
        lastHash.remove(player.getUniqueId());
    }
}
```

另外建议在配置里加一个 `max-claims`（例如 512），`ClaimService` 超限时按到玩家的平面距离取最近的一批，从根上避免大包。

### S5 领地变更事件里同步 `refreshAll()`：批量操作直接把主线程打死

**位置**
- `server/src/main/java/com/horizonkk/pmxxlclaims/listener/ClaimChangeListener.java:23-56`（7 个 handler 全都是 `publisher.refreshAll()`）
- `server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:64-68`

**现象**
每个事件 = 在线人数 × 1089 次 `ChunkRef` 查询 + 编码 + deflate，全部同步在主线程。设 50 人在线、单次查询 1 ms：

- 单次事件 ≈ 50 ms 主线程停顿；
- `/resadmin removeall`、某个插件批量创建 500 个领地、WorldEdit 式的大范围 res 操作 → 500 × 50 ms = **25 秒卡死**（TPS 直接归零）；
- `ResidenceAreaAddEvent` 是**按区域**触发的，一个 3 区域的领地创建就会有 3 次全量刷新。

**修法**（改动小、收益大）

```java
// ClaimChangeListener：7 个 handler 统一改成
private void markDirty() { publisher.markDirty(); }

// ClaimPublisher
private volatile boolean dirty = true;

public void markDirty() { dirty = true; }
public void markDirty(UUID uuid) { dirty = true; }

// 保留一个 1 秒的定时任务，只有 dirty 才真正刷
task = Bukkit.getScheduler().runTaskTimer(plugin, () -> {
    if (!dirty) return;
    dirty = false;
    refreshAll();
}, 20L, 20L);
```

进阶：把 `collect()` 的结果做"世界 + chunk 区域"缓存，事件里只失效受影响的世界，玩家只重算自己覆盖的区域。

### S6 推送静默 30 秒后客户端误判"服务端没插件"，自动查询器开始刷 `/res show`

**位置**
- `server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:56-59`（哈希不变直接 return，不发任何包）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCache.java:17`（`ACTIVE_MS = 30000`）、`:58-60`（`isActive()`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/AutoScanner.java:27-29`、`:47-63`
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/MinimapRenderer.java:96`（`if (!ClaimCache.isActive())` 切兜底）

**现象**
服务端只在"内容变了"时发包。玩家站着不动、周围领地没变化 → 30 秒后 `isActive()` 变 false → `AutoScanner` 复活 → 玩家一走动就每 1.5 秒发一次 `/res show`（`intervalMs` 最小 500ms，即最高 2 次/秒）。后果：

- 聊天刷屏 / 触发服务器的命令冷却、反刷屏、甚至反作弊踢人；
- 叠加 S1，这 3 秒窗口内所有含关键词的系统消息被吞；
- 玩家在**没有 Residence 的别的服务器**上同样会发 `/res show` → 满屏 "Unknown command"。

**修法（两端各改一点，双保险）**

服务端：加心跳，内容不变也每 5 秒补发一次（顺便解决了"客户端重进世界后数据过期"）：

```java
private static final long HEARTBEAT_MS = 5000L;
private final Map<UUID, Long> lastSentAt = new HashMap<>();
...
long now = System.currentTimeMillis();
boolean changed = !Objects.equals(previous, hash);
boolean stale = now - lastSentAt.getOrDefault(id, 0L) > HEARTBEAT_MS;
if (!changed && !stale) return;
...
lastSentAt.put(id, now);
```

客户端：把"服务端存在"做成粘性状态，而不是 30 秒滑动窗口：

```java
// ClaimCache
private static volatile boolean serverMode;      // 收到过一个合法 PMC1 就 true
// accept() 里 serverMode = true;
// 注册 ClientPlayConnectionEvents.DISCONNECT → serverMode = false; clear(); lastPacketAt = 0;
```

`AutoScanner.tick` 改成 `if (ClaimCache.isServerMode()) return;`，`isActive()` 只留给调试显示。

### S7 `ChatParser` 的 `Integer.parseInt` 未防护：异常从聊天事件逃出 → 断连

**位置**
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/ChatParser.java:44-58`（`Integer.parseInt` 在 `:51-53`）
- `client/src/main/java/com/horizonkk/pmxxlclaims/client/PmxxlClaimsClient.java:31-37`

**现象**
`COORD` 正则是 `(-?\d+)`，不限位数。任何系统消息里出现 `X: 12345678901234567890 Y: 1 Z: 2` 这种 20 位数字（插件打印哈希、坐标溢出、玩家昵称里带数字的公告……），`Integer.parseInt` 抛 `NumberFormatException`。它发生在 `ClientReceiveMessageEvents.GAME` 回调里，Fabric 不捕获 → 冒到 `MessageHandler#handleSystemMessage` → netty `exceptionCaught` → **"Internal Exception" 断连**。

**修法**

```java
private static final Pattern COORD = Pattern.compile(
    "X\\s*[:：]\\s*(-?\\d{1,7}).{0,12}Y\\s*[:：]\\s*(-?\\d{1,7}).{0,12}Z\\s*[:：]\\s*(-?\\d{1,7})");
...
try {
    pendingCoords.add(new int[]{Integer.parseInt(g1), Integer.parseInt(g2), Integer.parseInt(g3)});
} catch (NumberFormatException ignored) { return; }
```

并在事件注册处统一包一层 `try/catch (Throwable)`（聊天/网络回调里任何第三方异常都不该让客户端断线）。

## 2. 中等问题（性能 / 健壮性）

### M1 每跨一个区块就做 1089 次 `ChunkRef` 查询，且 `ChunkRef.hashCode()` 只有 `x ^ z`

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/claim/ClaimService.java:45-54`、`server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:53`

**量化（结构分析，非压测）**
- `ResidenceManager$ChunkRef#hashCode() = x ^ z`（反编译已核实）。这不是一个好的散列：一个几千条领地的私服，索引里可能有几万个 chunk 条目，而 `x^z` 在 ±1024 区块范围内只有 ~2000 个可能值 → 平均桶长几十到几百，`get` 退化成桶内线性扫描。
- 一次 `getResidences` = 1089 次 `Map.get`，合计约 **1089 × 桶长** 次 `equals`：桶长 20 时 ~2 万次，桶长 200 时 ~20 万次；再加 1089 个 `ChunkRef` 对象 + 内部一个 `HashSet` 的分配。
- 50 人在线、每 2 秒全量巡检 = 25 次查询/秒 → 单次 0.5~10 ms（视索引规模），主线程占 1~25%；**跨区块事件**（每玩家 0.8~1 秒一次）在这个基数上再叠一层，实际是 2~3 倍。

**修法（按性价比排序）**
1. **按 chunk 缓存**：`Map<Long, List<ResidenceRef>>` 存"该 chunk 命中的领地"，用 Residence 的 7 个事件做失效，玩家移动时只算新增的那一列 chunk（增量），成本从 O(R²) 降到 O(R)。
2. **缓存快照**：`Side = 33` 的窗口结果按"玩家所在 chunk"缓存 2~5 秒，同一 chunk 内重复请求直接命中。
3. **换算法**：直接遍历该世界的领地列表（`getResidences()` 的 name→res 表）做 AABB 相交，几十~几千个对象的一次遍历通常比 1089 次哈希查找更便宜，且没有 hash 冲突放大。
4. 至少把 `refs` 与 `ChunkRef` 对象复用（现在每次 new 1089 个）。

### M2 `radius-chunks` 钳制到 64 是"配置即炸"

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/claim/ClaimService.java:33`、`server/src/main/resources/config.yml:1`

(2×64+1)² = **16641** 个 ref，是默认半径（1089）的 **15 倍**；按 M1 的桶长模型，单次查询从 ~2 万次 equals 涨到 ~30 万次（桶长 20）到 ~300 万次（桶长 200），单次 10~100 ms；50 人每 2 秒 → 主线程直接饱和。`PLAN` 里写的是钳制 4..48，实际代码是 1..64，文档也不一致。

**修法**：`Math.max(2, Math.min(32, radius))`，并在 `onEnable` 里对超限值打一条 warning；`config.yml` 加注释说明 32 已是上限。

### M3 主线程同步 collect + encode + deflate

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:53-60`、`server/src/main/java/com/horizonkk/pmxxlclaims/net/ClaimCodec.java:86-98`

`Deflater(BEST_SPEED)` 对 20~60 KB 的 body 大约 1~3 ms，加上 1089 次查询与对象分配，单次刷新 3~10 ms。跨区块事件是高频的，玩家一多就会看到 40~80 ms 的周期性 spike（MSPT 抖动）。

**修法**：主线程只做"取快照"（Residence 不是线程安全的，必须在主线程读），把 `encode + deflate` 丢到 `CompletableFuture.supplyAsync` / 一个单线程 Executor，编码完成后再 `runTask` 回主线程 `sendPluginMessage`（发消息本身要在主线程）。注意加"同一玩家的旧任务作废"（用一个递增的 `revision` 比对）。

### M4 断线/换服不清缓存，旧服的领地带到新服

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCache.java:19-21`、`client/src/main/java/com/horizonkk/pmxxlclaims/client/PmxxlClaimsClient.java:26-52`（没有注册 `ClientPlayConnectionEvents.DISCONNECT`）

`byWorld` 只在收到新包时整体替换。退出服务器后 30 秒内 `isActive()` 仍可能为 true，且 `claimsFor("minecraft:overworld")` 在**任何**服务器的主世界都命中 → 在别的服看到上一个服的领地色块，或者换服后旧领地被当成"已知领地"影响 M15。

**修法**：注册 `ClientPlayConnectionEvents.DISCONNECT` → `ClaimCache.clear(); ClaimStore.clearSessionFlag(); AutoScanner.reset(); ChunkColorCache.clear();`；`JOIN` 时也清一次（防止代理切服不触发 DISCONNECT）。

### M5 `ChunkColorCache` 的 key 不含世界/维度

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ChunkColorCache.java:20`（`long key = (chunkX << 32) ^ (chunkZ & 0xFFFFFFFFL)`）、`:26-28`、`:71-73`（`clear()` 从未被调用）

下界/末地沿用主世界同坐标区块的颜色；而且下界坐标是 1:8 缩放，缓存完全错位。`clear()` 是死代码。

**修法**：key 里混入 `world.getRegistryKey().hashCode()`（例如 `((long) world.hashCode() << 40) ^ ...`），或换成 `Map<RegistryKey<World>, Long2IntMap>`；在 `JOIN/DISCONNECT` 里 `clear()`；顺便把 `CACHE.clear()` 的"超过 8192 全清"改成 LRU（全清会导致一次性大量重采样，正好发生在长途飞行时）。

### M6 HUD 每帧重复分配与全表扫描

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/MinimapRenderer.java:84-109`（`collect`）、`:88`/`:101`（每条领地 new 一个 `ArrayList` + 每个 box new 一个 `int[]`）、`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimStore.java:60-68`（兜底模式下 `forWorld` 每帧 O(n) + synchronized + new list）

每帧：13×13 = 169 次 `fill`（`MinimapRenderer.java:58-68`，注意 `chunkRadius = SIZE/32+2 = 6`，而可视区只需要 8×8，多算了 2.6 倍）+ N 个领地 × 5 次 `fill` + 每帧重建 `Draw`/`int[]`。60 帧下轻松几千个对象/秒。

**修法**
- 缓存 `List<Draw>`，只在 `ClaimCache` 版本号变化（`accept` 里 `version++`）或玩家跨 chunk 时重建；
- `chunkRadius` 改成 `SIZE / 32 + 1`（=5），可视区已经够覆盖；
- `ClaimStore.forWorld` 改成按世界分桶（`Map<String, List<KnownClaim>>`），避免每帧全表扫。

### M7 scissor 没有 try/finally

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/MinimapRenderer.java:51`、`:75`

正常路径成对；一旦 `collect/drawOne` 抛异常（例如空指针、坏数据），`disableScissor` 不执行。虽然异常大概率直接崩到崩溃报告，但如果被上层某处吞掉，后续所有 HUD 都会被裁到小地图矩形里，表现为"整个界面消失"。

**修法**：

```java
context.enableScissor(left, top, right, bottom);
try {
    ...
} finally {
    context.disableScissor();
}
```

### M8 以"领地名字"做全局去重键与 id

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/claim/ClaimService.java:95`（`name.hashCode()` 当 id）、`:101-105`（`seen` / `unique` 都以 name 为 key）

Residence 只保证"同一父领地下的子领地名唯一"。两个不同父领地下的同名子领地、或主领地与子领地同名时，后者会被 `seen.add` 挡掉 → **静默丢领地**。另外 `String.hashCode()` 撞车（"Aa"/"BB"）时 id 相同，虽然当前客户端不用 id，但协议里留着就是隐患。

**修法**：去重键换成 `parentName + "/" + name` 或直接用 `ClaimedResidence` 对象身份（`IdentityHashMap`/`Set<ClaimedResidence>`）；id 换成"世界名 + 名字"的 64 位哈希，或者干脆删掉 id（见 N3）。

### M9 一条领地的世界由"最后一个区域"决定，无区域的领地被丢进 `""`

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimCache.java:34-42`

`world` 在 area 循环里被反复覆盖；`areas` 为空或 worldIndex 全非法时 `world = ""`，领地进 `byWorld[""]`，永远渲染不到。当前服务端只发单世界，属于"潜在"，但代码没有表达"一条领地只能属于一个世界"的约束。

**修法**：取第一个合法 area 的 world 后 `break` 校验其余一致；`areas` 为空直接丢弃并计数；或者在协议里把 world 提到 claim 级（见协议简化建议）。

### M10 `ClaimStore` 无上限、无 TTL、主线程写盘

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClaimStore.java:29`（全局静态 `LinkedHashMap`）、`:78-81`（`forgetWorld` 从未调用）、`:117-149`（`Files.writeString` 在调用线程）、`:26`（`updatedAt` 从不使用）

跑过的每个服务器、每个世界的每条领地都会永久留在内存和 `config/pmxxlclaims-claims.json` 里，改名后旧名也留着。

**修法**：加最大条数（如 2000）与 `updatedAt` 淘汰；`saveIfDirty` 改成异步（`CompletableFuture.runAsync`）或至少合并到每 5 秒一次；`forgetWorld` 在换世界时按需调用。

### M11 `ClientConfig` 一半是死配置

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ClientConfig.java:17,30-32`（`showCount` 从未被读取，`MinimapRenderer.java:77` 无条件画）、`:59-69`（`save()` 只在文件不存在时调用，之后永远不会写回）、`MinimapRenderer.java:27`（`visible` 不持久化）

**修法**：要么接上（`if (ClientConfig.showCount())`、关掉时 `save()`、`visible` 存进配置），要么删掉。

### M12 `/claimsmap reload` 后命令持有旧 `ClaimService`

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/PmxxlClaims.java:50-54`、`server/src/main/java/com/horizonkk/pmxxlclaims/command/ClaimsMapCommand.java:23,59`

`reloadPlugin()` new 了一个 `ClaimService` 交给 publisher，但 `ClaimsMapCommand.service` 还是构造时那个，`/claimsmap debug` 继续按旧半径/旧 `send-owner` 输出，容易在排查时被误导。

**修法**：`ClaimsMapCommand` 不存 service，改成 `plugin.getPublisher().service()` 动态取；或者 reload 时重建命令执行器。

### M13 `fabric.mod.json` 版本约束过宽

**位置**：`client/src/main/resources/fabric.mod.json:13-18`

`"minecraft": "~1.21.11"` 允许 1.21.12+，但本模组用了 `HudElementRegistry`、`PayloadTypeRegistry`、`PacketApplyBatcher` 这些强版本相关 API，小版本一变就可能二进制不兼容；`"fabric-api": "*"` 没有下限（`HudElementRegistry` 是较新才有的）。

**修法**：`"minecraft": "1.21.11"`（要兼容再加 `"${minecraft}"` 之外的范围），`"fabric-api": ">=0.141.0"`。

### M14 服务端用 spigot-api 1.21.4 编译、跑在 Purpur 1.21.11

**位置**：`server/pom.xml:48-52`

`api-version: '1.21'` 会把不匹配藏起来；目前用到的 API（Messenger/Player/scheduler）在 1.21.4→1.21.11 之间是稳定的，所以能跑，但一旦要用电纸/新版 API 就会踩坑。

**修法**：换成 `io.papermc.paper:paper-api:1.21.11-R0.1-SNAPSHOT`（provided），并加 `<release>21</release>`（代替 source/target，能真正校验 API 可用性）。

### M15 `AutoScanner` 的状态机有洞

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/AutoScanner.java:14`（`QUERIED` 只按 chunk 存）、`:35-38`（换世界只重置 `lastChunk`）、`:50-59`（命中已知领地就永久标记已查）、`:66-77`

- `QUERIED` 的 key 只有 chunkX/Z → 两个世界同坐标互相污染，换世界后该 chunk 永远不再查；
- `insideKnownClaim` 命中就 `QUERIED.add(chunk)` 且**不发命令**，一旦领地后来被删（数据已过期），该 chunk 永远不会被重新确认；
- `QUERIED.size() > 8192` 时全清，会把所有 chunk 变回"未查"，紧接着一阵密集查询。

**修法**：key 改成 `world + chunk`；加过期（`Map<Long, Long> queriedAt` + 10 分钟 TTL）；淘汰用 LRU 而不是 clear；`insideKnownClaim` 命中时也记录时间戳而不是永久。

### M16 `ChatParser` 一行只取第一个坐标三元组，`/res show` 若同行打印两角点就永远解析不出来

**位置**：`client/src/main/java/com/horizonkk/pmxxlclaims/client/ChatParser.java:44-58`（`coordMatcher.find()` 只调用一次）、`:70-87`（要求 2 个坐标且偶数）

Residence 的 `/res show` 在不同版本/语言下可能是"一行两个角点"或"坐标 + 尺寸"，一旦一行里有 2 个三元组，当前代码只取第一个，`pendingCoords` 永远是奇数 → `flushIfComplete` 永远返回 → 数据丢失。另外 `looksLikeCoordinates`（`:66-68`）把"含 3 个及以上数字"的领地名判成坐标，会误拒合法名字（如 `mc2024`）。

**修法**：用 `while (coordMatcher.find())` 收集一行内所有三元组；`looksLikeCoordinates` 换成严格匹配 `^[-\d\s:,XY Z]+$` 或直接不看名字内容。

### M17 `accepts()` 的 `isEmpty()` 兜底是无效功

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/publish/ClaimPublisher.java:74-77`

`CraftPlayer#sendPluginMessage` 内部就是 `if (channels.contains(channel)) sendCustomPayload(...)`（反编译已核实），**原版客户端本来就不会收到**。所以 `isEmpty()` 分支除了让原版玩家也走一遍 1089 次查询 + 编码 + deflate 之外，没有任何作用。Bungee/Velocity 转发场景下 `getListeningPluginChannels()` 可能为空，这时它反而有用——但那是"代理不转发 register"的特例，应该显式配置。

**修法**：默认 `channels.contains(CHANNEL)`，配置项 `assume-client-unregistered` 打开时才回退到 `isEmpty()`；顺便把"发给谁"变成可配。

### M18 `getResidences` 返回空集合时无法区分"这个世界没领地"和"Residence 没有该世界的索引"

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/claim/ClaimService.java:54-61`

`ResidenceManager#getResidences(String, List<ChunkRef>)` 在 `chunkResidences.get(world) == null` 时直接返回空 `HashSet`（反编译已核实）。世界被 `removeChunkList`（卸载）或该世界刚加载、索引还没建时，会**静默变成"半径内没有领地"**，客户端收到空包后会把整张图清空——这比"不发包"更糟。

**修法**：Residence 没有公开 API 能区分这两种情况（`getWorldNames()` 读的是 `plugins/Residence/Save/Worlds` 目录，`getResidenceMapList(String, boolean)` 的第一个参数是玩家名不是世界名，二者都不可用）。所以只能在协议层解决：给包头加一个 `status` 字节（0=正常，1=世界未索引/数据不可信），索引缺失时发 status=1，客户端收到后**保留旧缓存**而不是清空；同时服务端每 30 秒最多 log 一次 warning，方便定位。

### M19 `ClaimCodec.encode` 吞掉 `IOException` 返回半截 body

**位置**：`server/src/main/java/com/horizonkk/pmxxlclaims/net/ClaimCodec.java:67-68`

`DataOutputStream` 写 `ByteArrayOutputStream` 实际不会抛 `IOException`，但 `catch (IOException ignored)` 会在将来换成别的输出流时把"写了一半的报文"当成正常数据发出去。

**修法**：改成 `throw new IllegalStateException(e)`，让 S4 的 catch 记日志并不发。

### N6 `config.yml` 没有注释、没有校验反馈
`server/src/main/resources/config.yml:1-2`：建议加注释说明单位（chunk）、上限、`send-owner` 只影响报文不影响显示（见 N3），并在 `onEnable` 里对越界值打 warning。

### N7 命令输出中英混用、硬编码
`server/.../ClaimsMapCommand.java:34`（"no permission"）、`:38-39`（英文 usage）、`:55`、`:68`；`PmxxlClaims.java:39`。建议走 `config.yml` 的 message 段或至少统一中文。

### N8 渲染常量全部硬编码

### N9 `flush()` 与 `tick()` 重复调用 `saveIfDirty`
`client/.../ChatParser.java:97` 与 `:104`：`tick()` 里 `flush()` 之后又调一次，无害但多余。

## 5. 能明显简化的复杂度

1. **协议的世界表**：服务端 `ClaimService.collect` 里 `worlds` 永远只有 1 个元素（`ClaimService.java:90-92`），客户端却为此维护了 `worldIndex`→`worlds[]` 的间接层（`ClaimCache.java:36-38`）和"最后区域定世界"的歧义（M9）。直接用 `String worldKey` 放头部，字段和分支都能删。
2. **id 字段**：`name.hashCode()` 在客户端只被存进 record，没有任何 keying 作用。删。
3. **Y 字段**：客户端 `ClaimCache.Box` 只有 XZ。删（或留作 v2 的 3D 判定）。
4. **两条数据源的分叉**：`ClaimCache.Claim` 与 `ClaimStore.KnownClaim` 两套结构，`MinimapRenderer.collect` 里写了两遍几乎一样的转换（`MinimapRenderer.java:87-107`）。抽一个 `RenderClaim(name, color, List<int[] boxes>)` 的工厂，两处共用。
5. **`ClaimData` 只承载两个 record**，可以并进 `ClaimService`（或改名 `ClaimModel`），少一个文件。
6. **`send-owner`**：服务端花了配置项和字段，客户端从不显示。要么实现（PLAN 里的"第二行归属者"），要么删掉（S/N3）。
