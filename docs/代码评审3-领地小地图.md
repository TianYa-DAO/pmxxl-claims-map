## 二、新发现问题

### 严重

#### X1【严重】渲染缓存不感知 `ClaimCache.isActive()` 过期：插件停用后地图永久冻结，兜底永不接管

**位置**：`MinimapRenderer.java:25-28,95-129`（缓存键 `:96-99`，`isActive` 判定 `:112`）；`ClaimCache.java:7,45-47`。

**机理**

```java
int packets = ClaimCache.packets();
int version = ClaimStore.version();
if (worldId.equals(cachedWorld) && packets == cachedPackets && version == cachedVersion) {
    return cachedDraws;                 // ← 时间导致的 active 过期不在键里
}
...
if (!ClaimCache.isActive()) { ... ClaimStore 兜底 ... }   // ← 只有重算时才会走
```

`isActive()` 是**时间**函数（`now - lastPacketAt < 60000`），但缓存键只有"世界 + 包计数 + ClaimStore 版本"。服务端插件被 `/reload`、卸载或崩溃后：

1. 不再有包 → `packets` 冻结；不再有解析 → `version` 冻结；
2. 60 秒后 `isActive()` 变 false，但 `draws()` 仍然命中旧列表，**把缓存里那份推流数据一直画下去**；
3. `ClaimStore` 的兜底分支永远进不去——除非玩家换维度（worldId 变）或恰好解析出一条新领地（version 变）。

**后果**：B3 想解决的"地图永久冻结、兜底不接管"**一模一样地发生**，而且更隐蔽（客户端看起来还有数据）。玩家会按过期的领地边界盖房/圈地。

**修法**（3 行，把"活跃态"变成缓存键的一部分）：

```java
private static boolean cachedActive = true;
...
boolean active = ClaimCache.isActive();
if (worldId.equals(cachedWorld) && packets == cachedPackets
        && version == cachedVersion && active == cachedActive) {
    return cachedDraws;
}
...
cachedActive = active;
cachedDraws = out;
```

更稳的做法：在 `ClaimCache` 里维护一个 `epoch`，每当 `isActive()` 发生 true→false / false→true 翻转就自增；渲染键用 `epoch`，语义更清晰。

### 中等

#### Y1 世界标识被 120 字节上限截断 → 客户端世界比对失败，整图静默空白

**位置**：`net/ClaimCodec.java:45,74-83`（`writeString(out, world)` 与名字共用 `MAX_STRING = 120`）；`ClaimCache.java:23,38-43`。

事件顺序：服务端 `Snapshot.world = player.getWorld().getKey().toString()` 是**完整**维度键（`ClaimService.java:62,120`），但编码时被 `writeString` 截到 120 字节；客户端拿完整 `worldId` 比对（`ClaimCache.claimsFor`）。

- 维度键长度 >120 字节（命名空间 + 长路径的数据包维度，例如 `mypack:dimensions/some/very/long/path`）→ 客户端 `world.equals(worldId)` 恒 false → `claimsFor` 返回空；
- 此时 `isActive()` 为 **true**（包是被正常接收的），所以 `MinimapRenderer.java:112` 的兜底也被跳过；
- 结果是**整张图只有地形、没有任何领地、没有任何日志**，心跳还每 10 秒把"坏世界名"重发一次。

这是本轮 #9 引入的**回归**（修复前世界串不截断，≤256 字节的维度键是好的）。

**修法**：世界与名字分开限长——服务端给 `world` 单独 512 字节上限，客户端对 `world` 用 512（其余字符串维持 256）；超过 512 的维度键在服务端记一次 WARNING（现实中几乎不存在）。名字/owner 保持 120。

```java
private static void writeString(DataOutputStream out, String value, int limit) { ... }
writeString(out, world, MAX_WORLD);   // 256
writeString(out, claim.name(), MAX_STRING);
```

#### Y2 按字节截断会切断 UTF-8 多字节字符

**位置**：`net/ClaimCodec.java:76-83`（`bytes = Arrays.copyOf(bytes, MAX_STRING)`）。

119 个 ASCII + 1 个三字节汉字 = 122 字节，截到 120 会把汉字切成半个序列；客户端 `new String(bytes, UTF_8)` 用 U+FFFD 顶替，名字末尾出现 `�`，两条长名字还可能截成同一串。不会崩、不会丢包，但显示与排查都会被误导。

**修法**：按码点截断，或在字节层面退回到字符起始字节：

```java
int end = MAX_STRING;
while (end > 0 && (bytes[end] & 0xC0) == 0x80) end--;   // 退到首字节
bytes = Arrays.copyOf(bytes, end);
```

（`bytes[end]` 是第一个被丢弃的字节；若它是续字节 10xxxxxx 说明切在字符中间。）

#### Y3 快照 TTL 等于巡检周期，M1 的主线程开销没有实质缓解（#14 未生效）

**位置**：`ClaimService.java:29,60-78`；`ClaimPublisher.java:49`。

- 巡检：`runTaskTimer(..., 60L, 60L)` = 每 60 tick；服务器不会快于 20 TPS ⇒ 相邻两次采集的墙钟间隔 ≥ 3000ms。
- 缓存：`now - cached.at() < 3000`；`at` 是**本次构建开始时**取的时间戳，只会让差值更大。
- 结论：站着不动的玩家每 3 秒必然 miss；跨区块换 key 也必然 miss。稳态命中率仍 ≈0。

量级：R=16 时每次 1089 次 `ChunkRef` 查询（`ChunkRef.hashCode = x ^ z`，33×33 范围内桶冲突极重），50 人 ⇒ 约 **1.8 万次查询/秒**在主线程；R=32 时 4225 次/人 ⇒ 约 **7 万次/秒**。本轮唯一的改善是周期 2s→3s（−33%）。

**修法**（任选）：
1. TTL 改成 15～30 秒（领地变更靠 `invalidate()` 兜底），这样站桩玩家每次巡检都命中；
2. 巡检前先比"区块 key 是否变化 + generation 是否变化"，未变直接跳过 `collect`（比 TTL 更直接）；
3. 真正的大头是把 `getResidences(world, 1089 refs)` 换成"该世界领地列表 + AABB 相交"，彻底摆脱 `ChunkRef` 哈希。

#### Y4 ClaimStore 的服务器键只到"连接地址"这一层：代理/多域名/单机三种行为都不完整

**位置**：`ClaimStore.java:45-53,82-91,101-107,151`。

| 场景 | 实际行为 | 问题 |
|---|---|---|
| 单机 | `getCurrentServerEntry()` 为 null 或 `address="local"` → 键 `local\|...` | 正确 |
| 同一服、两个地址（`play.x.com` / `ip:25565`） | 两套键 | 数据重复占 2000 上限；`insideKnownClaim` 只认当前键 → 会重复查询；旧服数据永不清理 |
| BungeeCord/Velocity 多子服 | 所有子服共用代理地址 | **子服之间串数据**：同名世界 + 同名领地会互相覆盖/互相显示；`insideKnownClaim` 命中后跳过查询（10 分钟） |
| 换服 | `forgetServer` 无调用方（`:101-107`） | 旧服数据永久留在 json 里 |

**修法**：地址归一化（小写、去默认端口、punycode）；JOIN 时把"上一次连接地址"记下来，若与当前不同则 `forgetServer(上次)`；代理多子服场景给一个配置项 `server-key`（默认取地址），由玩家手填子服名——客户端没法自己识别子服。

#### Y5 写盘竞态：`dirty` 先清后 CAS，CAS 失败或写失败都会丢这一批

**位置**：`ClaimStore.java:168-183`（`:174` 清 dirty，`:177` CAS）、`:185-212`（`:210-211` 吞 IOException）。

```java
dirty = false;                       // 先清
snapshot = new HashMap<>(CLAIMS);
...
if (!SAVING.compareAndSet(false, true)) {
    return;                          // 上一次写盘还没结束 → 这一批不写，且 dirty 已经是 false
}
```

窗口很窄（上一次 write 的 SAVING 尚未复位），但触发时这一批改动要等到**下一次 put** 才会再写；`write()` 的 IOException 也只吞不恢复 dirty，崩溃/磁盘满即静默丢数据。

**修法**：CAS 成功后再在锁内 `dirty = false` 并取快照；`write` 失败时置回 `dirty = true`。

#### Y6 超大包裁剪失败：每 3 秒重跑 9 次 encode + 一条 WARNING 洪水

**位置**：`ClaimPublisher.java:174-191`（`:177-190`），配合 `:81,96-108`。

`encodeSafely` 返回 null 时 `deliver` 不执行 → `lastSentAt` 不更新 → 该玩家 `heartbeat` 恒为 true → 每 3 秒重跑"1 次整包 + 8 次折半"的 encode/deflate，并打一条 `WARNING`（`:189`）。半径 32 + 密集领地时，这既是 CPU 浪费也是日志洪水（和 A2 同类的坑）。

**修法**：记住 `lastOversizeAt`，30 秒限频；或直接发送裁剪到 1 条后的包（让客户端至少看到最近的一条），只记一次 `fine`。

#### Y7 解析面仍是"全部系统消息"，NAME 正则过宽，仍可能造出伪领地

**位置**：`PmxxlClaimsClient.java:38-40`；`ChatParser.java:10,24-44`。

`ALLOW_GAME` 对每条服务端消息都调 `ChatParser.accept`（与查询窗口无关）。场景：某插件发 `区域: 商店`（命中 `ChatParser.java:10` 的"区域"分支）→ 1.5 秒内另一条带两组 `X:.. Y:.. Z:..` 的消息（传送/死亡坐标公告、另一个插件的保护提示）→ 生成一条名为"商店"的领地并落盘 `pmxxlclaims-claims.json`。B5 第二轮只修掉了"unnamed"，没修"不该解析"。

**修法**：`if (AutoScanner.inWindow() && !overlay) ChatParser.accept(...)`；NAME 正则锚到行首（`^(?:领地|領地|Land|Residence|Current Area)\s*[:：]`），去掉"区域"。

#### Y8 客户端解码失败完全静默；两端硬上限不对齐

**位置**：`client/ClaimCodec.java:36-38,58-70,106-108`；`ClaimCache.java:18-22`；`net/ClaimCodec.java:46,52`。

- `decode` 失败返回 null → `accept` 直接 return，**没有一行日志**（B6 当时要求的"warn once"没做）。排查"客户端 claims 恒 0"依旧只能靠猜。
- 客户端 `MAX_CLAIMS=8192`、`MAX_AREAS=512`；服务端对 claims 数和单条 area 数都没有对应上限。一条 >512 区域的领地（或半径 32 的极密集区）会让**整包**被拒；不过这种情况会在 60 秒后让 `active` 过期、自动回落兜底，属于"可自愈"。

**修法**：decode 失败 60 秒限频 `LOGGER.warn`（带长度/字段）；服务端 `encode` 前把 areas 裁到 512、claims 裁到 8192。

#### Y9 `refreshAll` 仍无逐玩家兜底（B2 残留，低风险）

**位置**：`ClaimPublisher.java:76,82-88,111-115`。

目前 `refresh` 里现实可抛的只有 `collect`（已被包住）；`accepts()`（`getListeningPluginChannels`）、`signatureOf()`、`runTaskAsynchronously` 都在 try 外。一旦其中任一在某个玩家上抛 RuntimeException，`refreshAll` 的 for 循环中断，**本轮后面所有玩家**收不到包，且只留下调度器的异常日志。

**修法**：`for (Player p : ...) { try { refresh(p); } catch (RuntimeException e) { log; forget(p.getUniqueId()); } }`。
